# Agent 自助接入与持续协作改进方案

日期：2026-11-22。状态：用户已确认目标；本文定义待开发方案，不代表功能已实现。

本文用于后续 AI 开发。先读本文，再读现有需求、技术设计、接入协议和协作代码。本文明确替代的旧规则以本文为准；其他已确认行为继续保留。实施前重新检查工作区和数据库版本，不按本文中的版本号盲目覆盖代码。

## 1. 要交付的结果

```text
用户在 AI-gent 点击“添加 Agent”
                 │
       复制邀请提示词和配对码
                 │ 粘贴到本机 Agent
                 ▼
Agent 自行访问本机配对接口、提交身份和运行组件线索
                 │
AI-gent 校验邀请、检查运行组件、登记 Agent
                 │
        AI-gent 接管持续运行
                 ▼
┌──────────────────── AI-gent，一个桌面程序 ────────────────────┐
│ Agent 注册表 → 持久消息队列 → 协作调度器 → 厂商运行适配器       │
│                      ↑                        │              │
│                      └── 回复、交接、状态 ────┘              │
│ 托盘 / 配对服务 / 恢复 / 暂停与停止 / 任务结果，全部由本应用负责 │
└──────────────────────────────────────────────────────────────┘
                               │ 现有本机执行协议
                               ▼
                      Codex / DeepSeek / 后续厂商
```

用户只使用 AI-gent 和已经安装的 Agent。无需再安装、启动或维护一个独立的连接软件。允许 AI-gent 启动厂商执行子进程；这不是要求用户维护另一个产品。

任务完成后，AI-gent 继续等待消息。Agent 被其他成员指派、@ 或收到明确交接后，AI-gent 自动启动或恢复对应执行会话。无需用户再次打开原厂窗口或重发提示词。

“持续在线”表示本应用能持续接收并调度任务，不表示大模型一直生成，也不要求每个厂商进程永久存活。无任务时不调用模型维持心跳。

## 2. 已确认要求与实现边界

| 编号 | 要求 | 实施约束 |
| --- | --- | --- |
| R01 | 添加 Agent 时复制提示词和配对码 | 自助配对是新 Agent 的主要入口，不以手填可执行路径为默认流程 |
| R02 | Agent 自己接入 | Agent 发起配对请求；AI-gent 检查并登记，不让用户代跑正常接入命令 |
| R03 | 接入后持续协作 | 等待新消息、自动接力、恢复上下文均由 AI-gent 负责 |
| R04 | 不增加独立连接软件 | 配对服务、队列、调度、托盘均在 Tauri/Rust 应用中运行 |
| R05 | 完成一轮后仍能接任务 | 单轮完成不会关闭调度器，不会把成员永久标记离线 |
| R06 | 用户随时插话和叫停 | 用户控制优先于 Agent 交接；停止后旧结果不能重新启动任务 |
| R07 | 保留已有数据和功能 | 保留项目、群、群内会话、消息、模型选择、技能、审批和任务结果 |
| R08 | 为 Mac 保留可实现的路径 | 协议和数据不写死 Windows；两平台分别适配路径、进程和打包 |
| R09 | 如实显示能力 | 不能自动调用的 Agent 不得显示“已接入，可持续协作” |

### 2.1 本期范围

同一台电脑、同一系统用户、一个 AI-gent 实例。本期只完成 Codex 和 DeepSeek 的完整闭环。Gemini 和 Claude Code 仅记录接入路线，并在公共接口和数据模型中留好位置；本期不开发这两家的适配器，不安装运行组件，不配置认证，不调用模型，也不开放可配对入口。注册表和调度接口允许增加其他厂商，但不宣称未知 Agent 已兼容。

不依赖云端中转。不开放局域网接入。不添加多人账号、跨电脑配对、手机唤醒或公开群。不接管任意已经打开的聊天窗口，不承诺继承用户粘贴邀请的那段原厂会话。

配对码是一次邀请，不是模型 API Key。原厂登录、模型凭证和额度继续由原厂运行组件管理。AI-gent 不要求 Agent 上报或复制这些凭证。

### 2.2 接入能力的实际边界

| Agent 情况 | 结果 |
| --- | --- |
| 能发本机 HTTP 请求，且 AI-gent 有匹配的运行适配器 | 可以自助配对；通过检查后持续协作 |
| 能发请求，但没有可被程序调用的运行接口 | 记录失败原因，不激活为可执行成员 |
| 没有命令执行或网络请求能力 | 提示当前会话无法自助配对，改在具有能力的本地 Agent 会话中粘贴 |
| 能调用 CLI，但 AI-gent 尚未实现该厂商适配 | 显示“此类型暂不支持持续协作”，保留非敏感诊断；不伪造成功 |

提示词只能触发已有能力。它不能把任何聊天产品自动变成可后台调用的 Agent。

### 2.3 四类 Agent 的接入方式与实施顺序

这里的四类均有程序调用路线，不属于“只能在窗口手动输入”的情况。需要区分“厂商提供调用能力”和“AI-gent 已完成适配”。前者不能代替后者。

| Agent | 使用的运行组件 | 应用与运行组件的通信 | 本期处理 |
| --- | --- | --- | --- |
| Codex | Codex App Server | 启动 `codex app-server --listen stdio://`，通过 stdin/stdout 交换 JSON-RPC 消息 | 复用 `codex.rs`，实现自助配对、实例身份和持续协作 |
| DeepSeek | DeepSeek Harness SDK 模式 | 启动官方 CLI host，使用 SDK profile，通过 stdin/stdout 交换 JSON-RPC 消息 | 复用 `deepseek.rs`，保留当前版本约束、权限和取消语义，完成相同闭环 |
| Gemini | 后续优先评估项目已预研的 Antigravity CLI / ACP；Gemini CLI 为另一候选 | `agy acp` 使用子进程 stdin/stdout JSON-RPC；Gemini CLI headless 可输出 JSON/JSONL 事件 | 只预留公共适配位置，暂不开发；未来选定一种运行组件后再实现 |
| Claude | Claude Code CLI / Agent SDK | CLI 可非交互调用，通过 stdin/stdout 输入任务并输出 JSON/JSONL；SDK 提供程序控制接口 | 只预留公共适配位置，暂不开发；未来先评估 CLI 是否满足事件、审批和中断要求 |

四家共用 AI-gent 的邀请、配对、注册表、持久队列、调度器、用户控制和任务结果。各家适配器只负责本家运行组件。持续收消息放在 AI-gent 中，不要求每家额外安装一个常驻连接程序。

**Codex 本期细则：** 延续 App Server 初始化、模型列表、`thread/start`、`thread/resume`、`turn/start` 和当前取消/审批处理。邀请中的运行线索仅用于查找并检查组件。新实例必须按自己的 agent_id 和群会话保存 thread 映射；不依赖配对时那段原厂对话持续运行。

**DeepSeek 本期细则：** 延续已验证 Harness `0.2.1-rc.2` 的 SDK 接入和独立 profile 实现。实际 RPC 方法以现有代码和该版本协议为准，不从命令名称猜测。保留现有会话恢复、工作目录、模型、工具权限和进程组取消行为。不能把单次 headless 文本调用替换成完整 SDK 模式后就宣称行为等价。

**Gemini 后续细则：** “Gemini”是成员展示/模型归属概念，实际运行组件须单独记录。沿用 [Gemini / Antigravity 接入预研](07-Gemini接入预研.md)，优先评估 Antigravity 的 `agy acp`。该入口由宿主启动子进程，以 JSON-RPC 连接 stdin/stdout，并使用 CLI 的登录与设置。另一候选 Gemini CLI 支持 `-p`/非交互输入以及 `--output-format stream-json`，可输出会话、消息、工具和结果事件；仍须单独核对会话恢复、审批和取消，不能只拿最终回复文本当完整执行协议。两条路线不是同一个协议，不能混用命令、凭证或会话 ID。未来接入时重新选择并固定路线，本期不作默认切换。

**Claude 后续细则：** 接入对象是 Claude Code，不是通过自动点击 Claude 聊天窗口完成任务。官方 CLI 的 `claude -p` 支持非交互运行，`--output-format stream-json` 支持流式结果，`--resume <session_id>` 支持恢复指定会话。后续适配应按 AI-gent 的实例/会话映射保存 session ID，不能用“恢复最近会话”代替精确归属。需要细粒度审批回调或 CLI 不能满足的中断控制时，再评估官方 Agent SDK。不能为了自动协作默认跳过权限，也不承诺复用普通 Claude 聊天产品的认证、历史或额度。

本节官方接口依据于 2026-11-22 核对：

- [Codex App Server](https://learn.chatgpt.com/docs/app-server)：执行协议和 stdio 入口；本项目实际调用以固定版本代码为准。
- [DeepSeek Harness CLI](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/README.md) 与 [SDK 说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/guide/python-sdk.md)：当前适配仍受本机已验证版本约束，不自动追随 master。
- [Antigravity ACP](https://antigravity.google/docs/cli/acp/)：`agy acp` 子进程与 stdin/stdout JSON-RPC。
- [Gemini CLI headless](https://geminicli.com/docs/cli/headless/)：程序调用及结构化事件输出。
- [Claude Code 程序调用](https://code.claude.com/docs/en/headless)：非交互调用、结构化输出和指定会话恢复。

官方接口存在不等于本项目已完成运行验收。Gemini、Claude 后续实施前必须重新核对版本、系统支持、登录方式、额度、事件、权限和取消行为。本次补充只写文档，不启动这两家的开发。

### 2.4 Gemini 与 Claude 的预留合同

预留位置指公共合同不再写死两家，不要求本期增加无功能适配器、空运行进程、假数据或占位执行成功。

| 位置 | 本期需要做到 | 后续接入时再做 |
| --- | --- | --- |
| Agent 身份 | agent_id 与 provider_kind 分离；不再用 codex/deepseek 联合类型充当成员实例 ID | 增加 Gemini、Claude 的真实运行配置和能力 |
| 运行组件 | 在运行配置中区分厂商和实际运行组件，不让 Gemini 模型名决定 CLI 协议 | 选定 Antigravity/Gemini CLI 路线；实现 Claude CLI/SDK 接入 |
| 适配器注册 | 按已实现的适配器查询支持类型，本期只有 Codex、DeepSeek | 新适配器实现合同后注册，避免修改整个调度器 |
| 配对入口 | 只允许为已实现类型创建邀请；未实现类型返回 `provider_not_supported`，不消耗邀请码 | 开放对应类型并执行本家真实能力检查 |
| 界面 | 新建邀请的可选列表只包含已支持类型；如显示后续类型，标为“计划接入”且不可点击配对 | 真实适配完成后开放邀请、模型和状态 |
| 会话与结果 | 保存实例、运行组件、原厂 session/thread ID 和执行尝试关联，不预设只有两种字段 | 映射 Gemini/Claude 原厂事件、恢复和取消 |
| 数据与调度 | 成员关系和队列按 agent_id 路由；无须为了第三家重建任务系统 | 按新适配器能力声明增加厂商运行槽与配置 |

本期不预创建 Gemini、Claude 的活跃成员或可用模型，不给它们生成默认会话，不运行存在性探测。收到这两类申请时，明确写“已有程序调用路线，AI-gent 适配尚未开发”，避免误写成厂商本身不支持后台调用。

## 4. 用户流程和界面

### 4.1 首次添加

1. 用户点击“添加 Agent”。
2. 输入显示名称，选择受支持类型。类型限制邀请可接入的运行适配器，避免未知类型取得执行身份。
3. 应用生成配对码和完整提示词，显示有效期，提供一个“复制邀请”按钮。
4. 用户粘贴给同机的本地 Agent。该 Agent 读取接入说明、识别自身运行组件、发起配对。
5. AI-gent 展示“收到接入请求 → 正在检查 → 已接入，等待任务”。检查失败显示具体原因和重试入口。
6. 配对成功后可直接私聊；用户选择加入的群。首次配对不默认把所有项目和私聊授权给该 Agent。

邀请创建是本次登记和非模型能力检查的授权。正常配对过程不再弹出第二次泛化确认。原厂工具对网络或命令的权限要求仍按其原有机制处理，提示词不能绕过。

### 4.2 邀请弹窗

显示名称、类型、配对码、过期时间、复制邀请、重新生成、取消邀请。配对码隐藏时可主动展开；弹窗关闭不取消尚未过期的邀请。

不让用户理解 HTTP、端口或 stdio 才能完成流程。技术诊断放在可展开的详情中。若应用重启导致邀请失效，界面明确要求重新生成，不让用户反复使用旧提示词。

### 4.3 配对状态与运行状态分开

| 维度 | 内部值 | 界面含义 |
| --- | --- | --- |
| 登记状态 | pending / validating / active / failed / revoked | 等待接入 / 检查中 / 已接入 / 接入失败 / 已移除 |
| 可用状态 | checking / ready / degraded / unavailable / disabled | 检查中 / 可接任务 / 需要处理 / 不可用 / 已停用 |
| 执行状态 | idle / queued / running / waiting_approval / cancelling | 等待消息 / 有任务排队 / 正在执行 / 等待批准 / 正在停止 |

“已接入”不等于模型认证和额度已通过真实执行检查。仅做本地握手时，详情写“运行组件已就绪；模型认证及额度将在首次执行时确认”。不要为展示绿色状态自动调用模型。

### 4.4 持续使用

- 关闭主窗口默认缩到托盘，后台协作继续。首次关闭时给一次清楚提示。
- 托盘提供打开窗口、暂停全部协作、恢复、彻底退出。菜单可看到运行及排队数量。
- 彻底退出会停止接单、保存状态并清理本应用启动的进程。电脑休眠或关机期间不承诺继续执行。
- 本期不自动安装开机启动项。未来增加该设置时由用户主动开启。
- 移除 Agent 采用撤销/停用方式，保留历史作者和任务证据；不直接删除历史关联。
- 正在执行的成员被移除时，先停止分派，按已有取消语义处理当前执行。未取消成功不能显示“已安全停止”。

## 5. 总体架构和责任划分

### 5.1 进程和通信

| 连接 | 本期方式 | 说明 |
| --- | --- | --- |
| React 界面 → Rust | 现有 Tauri IPC | 创建邀请、状态、用户控制；界面不直接访问本机配对端口 |
| 原厂 Agent → AI-gent | 本机 HTTP + JSON | 仅用于自助配对、查询本次接入结果 |
| 调度器 → Codex | JSON-RPC，stdio | 复用已存在的 App Server 逻辑 |
| 调度器 → DeepSeek | 当前 SDK JSON-RPC，stdio | 复用已有 Harness 适配 |
| 内部消息与交接 | SQLite 持久队列 + 进程内通知 | 通知可丢失，队列不能依赖内存 |

本期无需 WebSocket 或 SSE。原厂 Agent 完成登记后，不需要另跑一个永久轮询脚本。AI-gent 自己接收群消息并启动厂商运行组件。不要照搬 Pachat 云端监听链路到同机方案中。

### 5.2 后端模块建议

| 模块 | 职责 |
| --- | --- |
| `agents.rs` | 注册表、状态、能力、名称和实例查询 |
| `pairing.rs` | 邀请、配对码、幂等申请、接入检查 |
| `local_api.rs` | 本机 HTTP 监听、请求限制、协议分发 |
| `runtime/` | 小型统一接口；Codex、DeepSeek 适配复用现有实现 |
| `scheduler.rs` | 唯一后台调度、持久队列、租约、重试和恢复 |
| `collaboration.rs` | 保留协作业务：路由、任务边界、用户控制和交接 |
| `lib.rs` / 托盘模块 | 应用生命周期、服务启停、退出清理 |

模块名称是落地建议。可沿用现有合适模块，避免为目录结构重写稳定逻辑。禁止新增第二套独立的群任务系统或第二个调度循环。

### 5.3 身份模型

区分 `agent_id`（成员实例）和 `provider_kind`（codex、deepseek 等厂商）。显示名称和模型名不是身份。

同一厂商可以有两个不同名称、不同角色或模型配置的逻辑成员；它们可共用同一个原厂登录和运行组件，不因此声称账号隔离。实例身份在前后端和数据库中使用同一术语。

本期运行槽默认按厂商串行，一家同时运行一轮；Codex 与 DeepSeek 可以并行。不同逻辑成员即使同厂商，也必须隔离执行会话、配置和消息归属。不要把现有全局 Runtime 直接当成多实例隔离已经完成。

## 6. 配对协议 v1

以下路径、字段和错误码是 AI-gent 新设计，不是 Codex 或 DeepSeek 已有接口。实现前统一定义类型，不分别在提示词和服务端手写两套协议。

### 6.1 服务启动与监听

- Rust 启动时绑定 `127.0.0.1` 的系统分配空闲端口；不绑定 `0.0.0.0`，不自动改防火墙。
- 生成新的 `server_instance_id`，创建邀请时把实际 URL 和实例 ID 写入提示词。
- 邀请仅在本次实例中有效。应用重启后旧邀请作废；已激活的 Agent 注册记录继续有效。
- 开发版与正式版的数据目录、实例 ID 和凭证互不混用。重复启动同一数据目录时，第二个实例聚焦首个窗口或明确退出，不能再启动一个调度器。
- 服务绑定失败时，现有聊天可继续使用；添加 Agent 显示真实错误，不展示不可用的邀请地址。

### 6.2 邀请规则

默认有效期 10 分钟，一次使用。推荐 12 位无歧义随机字符、分组显示；必须用密码学安全随机数生成。邀请码存摘要，不在诊断日志或数据库中保存明文。

邀请码绑定邀请 ID、应用实例、期望厂商、拟用名称、过期时间和使用状态。重新生成立即使旧码失效。无效码连续失败按邀请和来源限速，例如 5 次后该邀请锁定，需重新生成。

### 6.3 接口

| 接口 | 认证 | 用途 |
| --- | --- | --- |
| `GET /local/v1/health` | 无 | 仅返回版本、协议号和实例 ID，不返回项目、路径和 Agent 列表 |
| `GET /local/v1/pairing-guide` | 无 | 返回静态 v1 接入说明，不含凭证和用户数据 |
| `POST /local/v1/pairings/claim` | 请求体内邀请 ID + 配对码 | 原子领取邀请，提交运行组件线索 |
| `GET /local/v1/pairings/{claim_id}` | 短期 claim 凭证 | 查询检查结果；不具备任务执行权限 |

Agent 不通过该 API 任意执行系统命令，不通过该 API 直接读项目文件。桌面管理接口继续走 Tauri IPC，不能因新增 HTTP 服务被全部开放。

`claim` 请求示例，示例中的值均为占位符：

```json
{
  "protocol_version": 1,
  "server_instance_id": "<邀请中的实例 ID>",
  "invitation_id": "<邀请 ID>",
  "pairing_code": "<配对码>",
  "request_id": "<本次领取生成的 UUID，重试时不变>",
  "provider_kind": "codex",
  "runtime_hint": {
    "executable_path": "<可选：本机绝对路径>",
    "version": "<可选：本机读取结果>"
  }
}
```

第一次合法请求返回 HTTP 202：

```json
{
  "claim_id": "<领取 ID>",
  "claim_token": "<仅能查询本次结果的短期凭证>",
  "claim_token_expires_at": "<UTC 时间>",
  "agent_id": "<待激活实例 ID>",
  "state": "validating",
  "poll_after_ms": 1000
}
```

首次返回后使用 `Authorization: Bearer <claim_token>` 查询。凭证放请求头，不放 URL；原厂 Agent 只在当前配对过程内存中使用，不要求写入自己的长期配置。

相同邀请、相同 request_id、相同请求指纹的重试，返回相同 claim 和 agent_id，不创建第二个成员。允许在邀请未过期的短窗口内幂等重试，服务端重签短期 claim 凭证并更新摘要；旧 claim 凭证随即失效。不同请求抢领已用邀请码返回冲突。领取和创建 pending 成员使用同一数据库事务。

状态查询返回 active、failed 或 validating，附 `reason_code`、可读说明及可重试性。不暴露 token、完整环境变量或原厂认证输出。检查总时间默认上限 60 秒；客户端遵守 poll_after_ms，等待至终态或凭证到期，不无限轮询。

建议错误码：`invitation_expired`、`invitation_used`、`invitation_locked`、`instance_mismatch`、`provider_mismatch`、`protocol_unsupported`、`runtime_not_found`、`runtime_rejected`、`runtime_version_unsupported`、`runtime_init_failed`、`validation_timeout`。错误响应统一为 `{error:{code,message,retryable}}`，使用合适的 4xx/5xx；不要把所有失败都返回成功码。

尚无已实现适配器的类型返回 `provider_not_supported`。先检查该条件，再领取邀请码；不能为 Gemini、Claude 的预留类型创建 pending 成员或启动运行组件。

### 6.4 运行检查与激活

1. 校验邀请码和类型，领取邀请；按期望类型选择应用内置适配器。
2. 将 runtime_hint 当作线索，不当作可信命令。由适配器检查可执行路径、文件类型、版本和协议握手。
3. 优先复用应用能独立发现的原厂安装；候选必须符合受支持安装布局、版本和可执行入口。用户本地显式配置的路径可作为另一来源。
4. 远端请求体不能注册 shell 脚本、任意 argv、环境变量、工作目录、插件或新的通用命令模板。不得对 Agent 提供的字符串执行 `shell -c`、`cmd /c` 或拼接 PowerShell。
5. 只运行适配器定义的无模型版本检查/初始化，禁止自动发“你好”消耗额度。检查阶段不得并发占用正执行任务的同一个运行槽；可排队检查。
6. 成功后事务激活成员、保存已核对的版本和能力，通知界面。失败保留原因，但不加入可执行成员列表。

请求方自报“支持 resume/cancel”不构成证据。只有适配器实际支持的能力才能写入有效能力集。没有可调用接口不能用“配对成功”替代接入成功。

持久信任记录保存在 AI-gent 本地数据库；本期无需把长期执行令牌交回原厂 Agent。配对码消耗后不能再管理该成员。退出原厂配对会话不影响后续协作。

### 6.5 本机接口边界

只接受直接来自回环地址的请求，不相信代理头。校验 Host 为当前回环地址和端口；拒绝带浏览器 Origin 的配对请求，不开放通配 CORS，防止普通网页直接调用。限制 JSON 大小为 32 KiB、字段长度和请求超时。HTTP 请求、错误堆栈、复制状态和导出均脱敏。

回环地址不代表身份认证；邀请码仍必须校验。该设计不防御已经控制同一系统账号的恶意本地程序。不得把它包装成对所有本地进程的强隔离。

## 8. 持续协作的执行合同

### 8.1 适配器接口

定义最小统一接口，统一输入输出，不重写厂商 Agent 循环：

| 操作 | 语义 |
| --- | --- |
| `inspect_runtime` | 无模型检查，返回实际版本、有效能力和就绪信息 |
| `list_models` / `list_skills` | 沿用厂商能力和错误语义，不用模型回答伪造目录 |
| `start_or_resume` | 按实例和会话启动，返回执行 ID、原厂 session/thread ID |
| `observe` | 归一化消息、工具、审批、结果、错误和交接事件 |
| `cancel` | 请求取消并确认结果，无法确认则 interrupted，不冒充成功 |
| `shutdown` | 仅清理应用启动并管理的相关进程树 |

每次调用都明确携带 agent_id、conversation_id、task_id、delivery_id、attempt_id、工作目录、模型及当前权限配置。`provider_kind` 只用于选适配器，不能代替 agent_id 路由。

每个 `(agent_id, conversation_id, workspace_revision)` 独立保存原厂会话映射。换群、群内新会话、项目目录变更都不能复用错误会话。配对时的原厂聊天与执行会话是两回事。

### 8.2 持久调度

所有需要执行的消息先落库，再通知调度器。唯一调度器由 Rust 应用生命周期持有，不能由聊天组件挂载和卸载控制。进程内通知用于及时唤醒，低频扫描只补偿漏通知，不调用模型探测空闲。

| 队列状态 | 含义 | 可否自动重新派发 |
| --- | --- | --- |
| queued | 已保存，未领取 | 可以，满足启用、任务及成员条件时 |
| leased | 领取但尚未确认开始 | 只有持久记录证明未开始时才可退回 queued |
| running | 已记录启动意图或确认原厂执行 | 不能仅因租约超时就重跑 |
| succeeded | 已保存终态和结果 | 不重复执行 |
| failed | 明确失败且不会继续运行 | 仅对已判定可重试的启动前错误重试 |
| interrupted_unknown | 可能已产生副作用，终态不明 | 先核对原厂终态；无法核对则等待用户处理 |
| cancelled | 用户停止或任务已关闭 | 不自动重发 |

持久租约记录 owner_instance、lease_until、attempt_id；默认租期 60 秒，每 15 秒由调度器续租。领取通过 SQLite 事务原子完成。启动前先保存 attempt_id 和启动意图，再调用厂商。只在可证明未启动的情况下安全重试。

投递采用“至少一次通知 + 幂等落库”，不承诺任意命令恰好执行一次。无法跨 SQLite 和外部进程原子提交；崩溃窗口必须由 interrupted_unknown 承接。

### 8.3 消息与自动交接

- 保留已有用户广播和明确 @ 行为。广播为每位实际成员各建一条投递，不能重复展示多份用户消息。
- 用户插话先持久保存；对应成员完成当前轮后优先处理。Agent 交接次之。
- 只有用户消息、明确指派、结构化交接或本期保留的普通正文 @ 兼容规则能触发执行；状态变化、工具日志和所有聊天输出不自动广播。
- 正文 @ 兼容解析必须排除引用、代码块和附件；同名显示名称不能猜目标。候选列表使用 agent_id；重名通过显示后缀区分。
- 新适配器优先产生 `handoff` 事件：包含目标 agent_id、源消息、当前任务、交接要求和证据引用。结构化事件和正文 @ 指向同一来源时合并去重。
- 每条来源消息对每位目标、同一任务代次最多建一条投递。发给自己不递归启动；跨群交接不在本期范围内。
- 收到交接的 Agent 必须读取对应群会话上下文及相关实际文件，不能只凭对方“已完成”宣布检查通过。

去重键至少包含 `(conversation_id, source_message_id, target_agent_id, task_generation)`。同一轮有多个独立交接要求时先合并成同一投递正文，或在下一版增加显式 handoff_id；首版不要靠随机 ID 绕过去重。

### 8.4 不同状态下的行为

```text
等待消息 → 保存投递 → 排队 → 执行 → 保存结果
    ↑                                  │
    └── 没有新交接 ─────────────────────┘
                         │ 有交接
                         └── 给目标成员排队
```

无新交接时回到等待，不定时让 Agent 互相问候。单轮结束不关闭群任务的可继续状态。任务已验收或明确关闭后，后到的 Agent 消息只归档，不自动重开任务；新的用户需求创建新任务。

保留每群每小时 100 次执行的现有频率保护。到限后暂停该群的自动派发、保留队列并给原因；时间窗恢复后仍需用户继续，避免界面显示暂停却自行恢复。配对检查和空闲扫描不计模型执行轮次。

重复相同内容和来源的交接直接去重。多轮没有新结果或证据的往返应暂停并给出可读原因，可采用连续 3 轮无新增交接依据的默认阈值；这是保护机制，不固定协作总轮数。用户可继续或调整任务，不以静默丢消息结束循环。

### 8.5 用户控制和文件并发

| 控制 | 必须发生的行为 |
| --- | --- |
| 暂停群任务 | 停止领取新投递；当前轮可结束，结果保存，交接留队不启动 |
| 恢复 | 按优先级继续仍有效的投递，不重新执行已完成轮次 |
| 停止 | 先增加任务 generation 并禁止派发，再取消当前轮和旧代次待办 |
| 暂停全部 | 调度器不领取任何新投递，连接和界面继续运行 |
| 彻底退出 | 停止接单、保存队列与尝试记录、有限等待取消、清理管理的进程 |

厂商事件携带 generation/attempt_id 归属。停止后到达的迟到结果可以归档为迟到事件，不能覆盖新任务状态或再发交接。新请求必须使用新的代次。

Agent 的文字不能冒充用户批准。现有 Codex 审批和 DeepSeek 的真实权限边界继续保留；自动协作不等于自动批准所有工具请求。

同一工作目录的并行执行沿用现有行为：不同厂商可并行，不同成员需明确分工；这不构成文件隔离。界面和交接需说明共用文件。不要因新增身份而放大现有并发或默默引入自动 worktree。需要隔离或写入锁时作为单独变更实现，不在本期顺带改写 Git 工作流。

## 9. 重启、断线与故障恢复

| 场景 | 恢复要求 |
| --- | --- |
| 窗口隐藏、前端重载、切换会话 | 后端继续；状态重新订阅或读取快照即可 |
| 单轮已结束，后来收到交接 | 自动恢复正确原厂会话并执行 |
| 厂商进程在启动前失败 | 保留投递；退避后有限重试，例如 1、3、10 秒，共 3 次 |
| 模型认证失败、无额度、版本不兼容 | 标记需处理；不无限重试，不切换账号或模型绕过 |
| 可确认无执行副作用的连接失败 | 按适配器错误分类有限重试；不按所有网络错误一律重发 |
| 运行中断线或崩溃 | 查询/恢复原厂执行状态；不能确认时标记 interrupted_unknown |
| AI-gent 重启 | 恢复注册表和 queued；重建调度器；不统一取消未开始输入 |
| 用户主动停止、关闭任务后重启 | cancelled 保持终态，不重跑旧队列 |
| 应用退出或电脑休眠 | 暂停本机能力；醒来后重新检查可用性，核对在途执行，再处理可安全派发项 |
| 队列保存失败、磁盘满 | 不启动未持久保存的任务；明确显示错误，避免出现无法追踪的执行 |

恢复启动顺序：数据库迁移 → 注册表 → 核对旧执行尝试 → 读取暂停与停止状态 → 启动调度器 → 启动配对服务 → 界面可用。服务启动失败只降级对应能力，不删除数据。

现有 `collaboration::recover` 对 queued/selected 的全局取消必须替换；`codex::recover`、`deepseek::recover` 和 `lib.rs` 退出路径也要一起审查。不能只在新模块保存队列，而旧恢复函数继续把同一任务取消。

| pairing_invitations | id、instance_id、expected_provider、display_name、code_hash、expires_at、state、失败次数、claim_id；短期记录定时清理 |

| agent_deliveries | id、agent_id、conversation_id、task_id、generation、来源消息、priority、state、lease、attempt_id、错误和时间；来源去重唯一索引 |
| agent_attempts | attempt_id、delivery_id、generation、启动阶段、原厂 run ID、开始/终态、错误分类、结果消息引用；delivery 下多次尝试各有记录 |

能复用已有 task/input/member/step 表时优先增列或做映射，不为了采用表名复制同一队列。上表是逻辑数据合同，不强制所有名称成为新表。最终迁移说明必须写清楚哪些复用、哪些新增，以及哪张表是调度事实来源。

任务和消息保留稳定 agent_id。历史作者已被撤销也能显示原名称和厂商。模型、思考强度、速度配置按实例与模型保存，不让同厂商不同成员覆盖彼此配置。

### 10.2 迁移规则

1. 从实施时实际 schema 版本递增，不改写已经发布的旧迁移。按现有方式先生成备份，再事务迁移。
2. 给现有 Codex 和 DeepSeek 建立注册记录；优先保留 `codex`、`deepseek` 为旧默认实例 ID，避免破坏历史引用。新增实例用稳定 UUID。
3. 旧记录标记为 legacy 来源，保留既有用户授权；启动做无模型检查后更新可用性，不伪造配对记录、不强迫旧用户重配。
4. 扩展 SQL 厂商枚举 CHECK、固定两位成员限制、任务内 codex_model/deepseek_model 及相关映射。需要重建 SQLite 表时保留主键、外键、索引和历史状态。
5. 群、群内会话、旧消息与任务 ID 不变。先明确现有 `agent` 列是身份还是厂商，再统一映射。不要全局字符串替换。
6. 保存旧排队消息的可恢复性；历史已经 cancelled 的输入不能因升级被复活。升级时状态不明的执行进入人工核对状态。
7. 新增逻辑与现有任务结果只维护一份来源链。重复迁移/重启不重复导入默认成员。
8. 迁移失败保持原数据库可恢复，显示错误并停止使用半迁移状态。旧版本遇到新 schema 应继续拒绝打开。

## 11. Windows 与 Mac

通信协议和任务数据共用；平台适配集中在运行组件发现、进程管理、托盘和打包。

| 项目 | Windows | Mac |
| --- | --- | --- |
| 配对接口 | 回环 HTTP | 相同 |
| 厂商调用 | 现有 stdio | 相同协议，使用 Mac 入口 |
| Codex 发现 | 现有 PATH 和桌面运行目录 | PATH 与已核对的原厂 app 入口；处理从桌面启动时 PATH 不同 |
| DeepSeek 发现 | 安装登记和受支持目录 | 核对 `.app/Contents/...` 的真实布局，不能沿用 exe 旁的相对路径 |
| 进程清理 | 保留已验证 Job Object | 对应用创建的进程组发出取消/结束；超时升级，不能杀同账号其他会话 |
| 窗口关闭 | 托盘继续 | 托盘/菜单栏继续；明确退出才清理 |
| 打包 | 当前 NSIS | 独立配置 Mac 应用包及安装交付；本机 Windows 不能证明 Mac 运行通过 |

用户最终交付只维护一个 AI-gent 应用。不要为了 Mac 增加独立守护进程安装器。本期开发可先完成 Windows 纵向闭环，但未完成 Mac 路径、取消和打包验收前，不能宣称 Mac 已支持。

## 12. 开发顺序与每阶段交付

各阶段在同一目标下连续实施，不能把“配对成功但无法持续协作”当最终交付。每阶段提交实现说明、变更文件、数据影响、用户验收步骤和未完成项。

| 阶段 | 开发内容 | 退出条件 |
| --- | --- | --- |
| S1：身份与迁移 | 注册表、默认成员迁移、动态身份、后端成员校验、前端动态列表 | 旧数据保持可读；新增逻辑成员不依赖两家固定字符串路由 |
| S2：自助配对 | 回环服务、邀请码、模板、领取幂等、版本检查、接入状态 | 用户复制一次邀请后，受支持 Agent 能自报并激活；失败不假成功 |
| S3：统一执行接入 | 适配器合同、实例模型/技能、会话映射、审批/取消/结果 | 新配对成员可从 AI-gent 私聊执行，原厂配对窗口可关闭 |
| S4：持续调度 | 唯一 Rust 调度器、持久投递、租约、恢复、去重、代次 | A → B → A 自动接力；空闲后新消息仍可启动；停止不复活 |
| S5：桌面生命周期 | 托盘、隐藏窗口、全局暂停、明确退出、实例互斥 | 隐藏不打断协作；退出有序清理；重启不启动双份任务 |
| S6：兼容与收尾 | 历史群会话/技能/审批/导出兼容、Mac 适配、文档同步 | 对照本节和验收矩阵逐项记录结果，平台未验收如实说明 |

S1–S4 可按实际依赖拆小提交，避免一次替换全部聊天逻辑。S1–S6 本期只覆盖 Codex、DeepSeek 和公共能力。Gemini、Claude 按第 2.3–2.4 节保留后续接入位置，不因完成本期阶段自动开始开发；之后由用户另行要求实施。不能以空接口或模拟成功冒充可扩展接入。

## 14. 验收矩阵

以下是后续由用户执行的验收步骤与预期，不是本次已通过的测试报告。开发 Agent 遵守 README 的既有约定：不主动运行测试、模型探针或界面测试，不额外编写测试，不为验证消耗模型额度，除非用户另行要求。

| 编号 | 场景与操作 | 必须看到的结果 |
| --- | --- | --- |
| A01 | 新建 Codex 邀请，粘贴到本机 Codex | 自动请求、检查并激活；界面有正确名称和实际运行版本 |
| A02 | 对 DeepSeek 完成相同操作 | 使用 Harness 适配成功；不要求用户自己手填正常安装路径 |
| A03 | 同请求重复领取、响应丢失后重试 | 只出现一个 Agent 和一个 claim，结果可继续查询 |
| A04 | 使用过期、撤销、错误厂商或已用码 | 明确拒绝；无第二个成员和后台执行 |
| A05 | 应用重启后使用旧邀请 | 明确提示实例/邀请失效，已激活成员不丢失 |
| A06 | 提交未知类型或任意 shell 路径/参数 | 不执行请求提供的命令；显示不支持或拒绝原因 |
| A07 | 配对后关闭原厂聊天，再从 AI-gent 私聊 | 能自动调用匹配运行组件；不依赖配对聊天存活 |
| A08 | A 实现，交给 B 复核，B 明确要求 A 修改 | 完成 A → B → A，来源、任务与结果可追踪 |
| A09 | 无任务等待 10 分钟后再交接 | 自动处理；空闲期间无模型心跳调用 |
| A10 | 运行中用户插话、再暂停和恢复 | 插话落库；暂停不派新轮；恢复按优先级继续 |
| A11 | 停止任务时旧运行晚到结果/交接 | 旧代次不启动新执行，不覆盖新任务 |
| A12 | 隐藏窗口、切群、前端刷新 | 后端持续；重新打开看到同一任务和队列 |
| A13 | 明确退出后重启，存在未启动 queued | 保留并安全派发；用户已暂停的仍暂停 |
| A14 | 启动外部执行前后分别异常终止应用 | 未启动项可恢复；不明运行不盲目重跑、不伪报完成 |
| A15 | 断网、无额度、认证失效或厂商进程退出 | 错误真实，有限重试，消息保留，无无限模型调用 |
| A16 | 两个群内会话、私聊、同厂商两实例分别执行 | 原厂会话、模型、历史和结果不串用 |
| A17 | 重复交接、自己 @ 自己、引用/代码中 @ | 不重复投递，不自循环，不把引用当新指令 |
| A18 | 达到每群频率保护，再等时间窗恢复 | 明确暂停、队列保留，用户继续前不自动派发 |
| A19 | 升级旧数据库，查看旧群、会话、任务与导出 | ID、作者和内容保留；备份存在；失败可恢复 |
| A20 | 停用/移除成员，再查看历史或发送给它 | 历史可读；不向已撤销成员执行新任务 |
| A21 | 同数据目录启动两次应用 | 只有一个调度器，不执行重复任务 |
| A22 | 浏览器网页请求配对端口、超大请求、猜码 | 拒绝不符合规则的请求；日志不出现凭证 |
| A23 | 待审批工具调用和取消失败 | 不自动放宽权限；取消未确认显示真实状态 |
| A24 | Windows 彻底退出/取消 | 本应用管理的进程被清理，其他原厂会话不受影响 |
| A25 | Mac 重复配对、执行、托盘、取消与恢复 | 分别记录实际系统、运行组件版本和结果；未跑则标记未验收 |
| A26 | 查看 Gemini/Claude 预留类型，尝试创建邀请或直接提交申请 | 不开放配对、不消耗邀请码、不创建成员、不启动组件；说明是本应用尚未适配，Codex/DeepSeek 接入不受影响 |

记录至少包括系统、应用版本、运行组件版本、操作步骤、预期、实际、脱敏证据和未完成项。持续协作必须用实际调用证明，不能只展示模拟在线状态；本地协议检查本身不调用模型。

## 15. 不允许作为完成的替代方案

- 只做一个“复制配对码”按钮，后台仍无配对接口。
- Agent 回答“接好了”，应用没有收到并核对真实请求。
- 只登记名字，任务仍要求用户去原厂窗口手动发送。
- 要求每位用户额外安装并维护另一个常驻监听软件。
- 让原厂 Agent 永久循环轮询维持在线，消耗模型额度。
- 只在 React 页面中运行接力计时器，隐藏/重载就停止。
- 重启时清空待办，或把不明副作用任务直接重发。
- 把所有正文自动广播，导致成员无休止互相回复。
- 通过放宽所有工具权限解决自动执行中的审批问题。
- 未适配运行接口就宣传“任何 Agent 粘贴提示词即可持续协作”。

## 16. 给后续开发 AI 的执行说明

1. 先读 README 的开发约定和本文；检查实际代码、未提交改动和 schema。保护用户已有文件，不恢复或删除无关改动。
2. 按 S1–S6 推进。先写出各阶段实际影响的调用方和迁移映射，再修改；不在本次文档之外擅自增加云服务、账号体系或独立后台安装器。
3. 需要新增依赖时按职责选最少的维护中组件：HTTP 服务、安全随机/摘要、单实例和托盘支持。不要自行手写 HTTP 解析或密码学；具体包与 API 实施时查正式文档，不把本文当版本锁。
4. 按已有 Tauri/Rust/React 结构实现。复用厂商登录、技能、审批、取消和任务证据，不用新模型 SDK 替换原厂执行环境。
5. 遵守用户自行测试的约定。交付时列出准确的验收步骤和“未测试，待用户验证”；需要实际模型调用的步骤标明会使用原厂额度。
6. 功能实施后同步 01/02/03/04/05 和 README，清楚区分已实现、待验收和后续范围。更新本方案状态，不把计划直接改成“已验证”。

最终完成条件：用户复制邀请给受支持的本地 Agent，AI-gent 收到真实请求并完成接入；关闭原厂配对聊天后，成员仍能在 AI-gent 内持续接任务、相互交接、保留上下文，用户可暂停和停止；无需额外维护独立连接软件。
