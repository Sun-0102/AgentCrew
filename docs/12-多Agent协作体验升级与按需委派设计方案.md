# 12 · 多 Agent 协作体验升级与按需委派设计方案（待开发）

> 状态：待开发  
> 目标范围：群聊多轮自主讨论优化、单 Agent / 项目会话按需委派、单聊平滑派生群聊

---

## 1. 背景与当前痛点

AgentCrew 目前已经具备单 Agent 会话（私聊 / 项目空间会话）以及多 Agent 群聊（`chat_groups` + `group_tasks` + `agentcrew-dispatch`）两套核心能力，但在实际高频开发与方案讨论中存在两个明显体验断层：

1. **群聊在“方案讨论”场景下容易一轮收口**
   - 当前 `agentcrew-dispatch` 的系统提示词主要围绕“派发编码子任务 → 验收 → 不合格返工”设计：
     - 被派发方被要求“仅按精确指令完成工作，无需 `@` 对方”（`src-tauri/src/collaboration/dispatch.rs`）。
     - 回执提示词要求统筹方“验收通过直接向用户汇报，如需返工再输出 `agentcrew-dispatch`”。
   - 结果：写代码时“派活 → 验收 → 打回返工”可以自动闭环，但在只读讨论/架构评审场景下，被派发方给出完整意见后，统筹方往往直接判定“无需返工”并一轮结束，用户不得不手动叮嘱“至少讨论 2 轮”。

2. **单 Agent / 项目会话中途需要另一个 Agent 时缺少轻量协作路径**
   - 日常开发 80%+ 的任务从单 Agent 会话开始（例如项目空间会话里先和 Codex 或 Gemini 聊需求/写代码）。
   - 做了一半想请另一个模型协助写代码、排查问题或做交叉 Review 时，目前要么另开一个群聊重新喂上下文，要么切 Agent 手动复制粘贴，心智割裂。
   - 若直接把单 Agent 会话原地强行改造成群聊，又会破坏“单主线、干净上下文”的体验，且涉及 `project_sessions` 与 `chat_groups` 两套表结构与外键约束的冲突。

---

## 2. 总体设计思路

保留 **“单主线会话”** 与 **“多 Agent 群聊”** 的各自优势，不二选一，而是形成三层递进协作体系：

| 场景 | 推荐形态 | 核心心智 |
| :--- | :--- | :--- |
| 日常开发、临时请另一模型写模块 / 做二审 | **单 Agent 会话 + 按需子任务委派** | 保持单一主负责人与干净主时间线，子任务过程折叠为卡片 |
| 架构头脑风暴、多模型公开辩论、用户随时插话 | **多 Agent 群聊（自主多轮协作）** | 平级同屏可见，支持自主多轮交锋直到达成共识 |
| 单聊进行到一半，确认需要长期多人同屏协作 | **一键派生为群聊** | 基于当前项目会话派生新群聊并带入上下文摘要，原会话保留 |

---

## 3. 分阶段实施方案

### 阶段一：群聊自主多轮讨论与评审闭环优化（优先，低风险）

**目标**：在不改变数据库和前端结构的前提下，让群聊在“代码执行”和“方案讨论/评审”两类任务中都能自主推进多轮，无需用户显式指定轮数。

#### 3.1 涉及文件
- `src-tauri/src/collaboration/dispatch.rs`
- `src-tauri/src/collaboration/prompt.rs`
- `src-tauri/src/collaboration/mod.rs`

#### 3.2 具体改造点
1. **丰富被派发方提示词（`dispatch.rs::encode_dispatch_input`）**
   - 保留“聚焦本次指令、完成后由系统自动回传”的约束。
   - 补充讨论/评审场景引导：当指令属于方案讨论、架构设计或只读复核时，鼓励主动指出原方案的盲区、边界风险、权衡取舍与不同意见，避免礼貌性附和。
2. **调整回执判定提示词（`dispatch.rs::queue_handoff`）**
   - 将当前仅面向“验收/返工”的回执文案扩展为同时覆盖“执行验收”与“讨论收敛”：
     - **执行类任务**：读取实际文件验收；通过则向用户汇报，未通过则继续 `agentcrew-dispatch` 打回修改。
     - **讨论/评审类任务**：若双方仍存在未解决的分歧、关键边界尚未对齐，或你整合后的最终方案尚未经过对方二次确认/查漏补缺，请继续使用 `agentcrew-dispatch` 推进下一轮讨论；仅当真正达成共识，或出现需要用户拍板的明确分歧时，才停止派发并向用户汇报。
3. **统一统筹者初始规则（`mod.rs::prepare_input`、`prompt.rs::build_prompt`）**
   - 明确说明 `agentcrew-dispatch` 不仅用于“派发代码修改”，也用于“多轮方案讨论与交叉复核”。
4. **放宽接力上限并同步调整安全熔断**
   - 将最大讨论/协作轮次上限从原来的 6 步放宽至 **100 轮**（对应 `MAX_DISPATCH_HOPS = 200`，即 100 次派发 + 100 次回执，后续可支持按群聊配置）。
   - 同步调整 `src-tauri/src/collaboration/mod.rs` 中的每小时 100 次执行频控（`recent >= 100`），避免长轮次讨论在未达轮次上限前被频控误暂停。
   - 维持连续 3 轮无新增工具依据的重复回复检测，并结合下述“长轮次上下文治理”防止无限空转。

#### 3.3 验收标准
- 用户仅发送 `@Gemini 你和 Codex 讨论一下 XX 方案，给我最终结论`（不写轮数）时，若首轮存在分歧或最终方案需交叉确认，双方能够自主进行多轮讨论后收敛汇报。
- 写代码场景的“派发 → 验收 → 打回返工 → 复验通过”链路回归通过，支持最多 100 轮自动协作，超限自动暂停等待用户确认。
- 现有 `cargo test collaboration` 全部通过。

### 阶段二：单 Agent / 项目会话的“按需委派”机制（核心体验升级）

**目标**：用户在单 Agent（尤其是项目空间）会话中，无需建群即可随时让当前主 Agent 呼叫其他已启用的本地 Agent 执行子任务或进行独立复核，结果自动回传给主 Agent，并在 UI 上以折叠卡片展示。

#### 3.1 交互与 UI 设计
1. **触发方式**
   - **自然语言触发**：用户在单 Agent 会话中直接要求（如“你先出方案，让 Codex 实现，然后你来 Review”或“请 Gemini 帮我只读复核刚才的改动”）。
   - **快捷 `@` 触发**：在单 Agent 会话输入框的 `@` 菜单中，除当前 Agent 外，列出本机已启用且可用的其他 Agent；用户 `@其他Agent` 时，作为委派意图交给主 Agent（或直接生成一条单次子任务委派，完成后结果仍汇入主 Agent 上下文）。
2. **消息流展示（子任务卡片）**
   - 主 Agent 发起委派后，在主消息下方渲染独立的**可展开子任务卡片**：
     - 折叠态：被委派 Agent 头像与名称、任务简述、实时状态（运行中 / 已完成 / 失败 / 已取消）、耗时、变更文件数。
     - 展开态：查看该子任务的完整回复、工具调用记录与独立 Turn Diff。
   - 不将子 Agent 的大段中间推理直接平铺进主会话消息列表，保持主时间线简洁可读。
3. **控制与审批**
   - 子 Agent 触发命令/文件修改审批时，复用现有审批卡片并明确标注发起委派的子 Agent 名称。
   - 用户点击“停止”时，级联取消正在运行的主 Agent 与子 Agent，保证无孤儿进程。

#### 3.2 后端架构设计（最大程度复用现有引擎）
1. **复用 `agent_sessions` 实现上下文隔离**
   - 被委派的子 Agent 不直接写入主 Agent 的原生 thread，而是绑定到独立的子任务 `runtime_conversation_id`。
   - 子 Agent 只接收：主 Agent 提炼的精确任务指令 + 当前项目工作区路径与必要工作区证据，避免将主会话全部历史塞入子 Agent 导致 token 膨胀。
2. **复用 `agentcrew-dispatch` 协议与调度机制**
   - 在单 Agent 会话的系统提示词中（当检测到本机存在其他已启用且有可用模型的 Agent 时），注入精简版派发能力说明与可用成员清单。
   - 主 Agent 一轮结束后，后端复用 `parse_dispatches` 解析派发块：
     - 若存在合法委派请求，自动启动对应子 Agent 执行；
     - 子 Agent 完成后，自动将结果与工具证据以回执形式投递回主 Agent，唤醒主 Agent 继续下一轮（验收、继续委派或最终汇报）。
   - 同样受最大接力步数上限保护，防止失控循环。
3. **数据结构扩展（新增独立迁移文件）**
   - 新增 `delegated_tasks`（或扩展任务表关联 `parent_conversation_id`、`parent_message_id`、`lead_agent`、`worker_agent`、`worker_conversation_id`、`status`、`summary`、`error`、`created_at`、`finished_at`）。
   - 保持 `project_sessions` / `private_sessions` 原有表结构与队列（`022_single_chat_queue.sql`）语义不变；当存在进行中的委派子任务时，主会话状态保持忙碌，新用户消息按既有排队逻辑处理。
4. **生命周期与崩溃恢复**
   - 在应用启动恢复流程中，扫描处于 `running` / `launching` 的委派子任务，按现有 `interrupted_unknown` 语义落终态，绝不静默丢弃或自动重放有副作用的操作。

#### 3.3 验收标准
- 在项目单 Agent 会话中，可由主 Agent 跨厂商委派另一个 Agent 完成只读复核或代码修改，完成后自动唤醒主 Agent 汇总。
- 委派过程在主会话中折叠为可展开卡片，可查看子 Agent 工具记录与文件变更。
- 中途点击停止、拒绝审批或重启应用后，主/子会话状态均能正确收敛，不出现“已完成但仍显示执行中”的状态残留。

### 阶段三（可选）：单 Agent 会话一键派生为群聊

**目标**：当用户确实希望从单 Agent 会话转为多人长期同屏讨论时，提供平滑升级入口，同时避免原地改表带来的架构复杂度。

#### 3.1 交互入口
- 在项目会话右侧栏「聊天成员」区域增加 **“添加成员 / 转为群聊”** 按钮。
- 点击后弹出成员选择器（默认勾选当前会话 Agent，允许再勾选 1 个及以上其他已启用 Agent），并提示：“将基于当前会话上下文在同项目下创建一个新群聊，原单聊会话会完整保留。”

#### 3.2 底层实现策略（派生而非原地改类型）
- 不直接修改 `project_sessions` 记录为 `chat_groups`，避免破坏定时任务关联、单聊排队表、归档状态及外键约束。
- 执行流程：
  1. 在同一 `project_id` 与 `workspace_path` 下创建新的 `chat_groups` + `group_sessions` 记录（复用现有群聊创建事务）。
  2. 将原项目会话的**核心上下文**（最近若干轮有效对话摘要或关键消息快照、以及当前绑定的知识库源）注入新群聊作为起始背景记录。
  3. 前端自动切换到新创建的群聊会话，原项目会话原封不动保留在项目会话列表中。

#### 3.3 验收标准
- 从项目单 Agent 会话点击“转为群聊”后，新群聊自动继承相同项目工作目录与知识库配置，新拉入的 Agent 能理解此前讨论背景。
- 原项目会话历史记录、定时任务、归档操作不受任何影响。

### 阶段四（配套底座）：长轮次上下文治理方案（支撑最多 100 轮讨论）

当协作上限放宽到 **100 轮** 后，虽然 `src-tauri/src/group_context.rs` 已对群聊拼装 prompt 做了固定字节预算（最近消息 12KB + 摘录 8KB + 检索 6KB），且前端已有 `ContextMeter` 监控展示（`crate::usage::conversation_context`），但目前**只做展示、未触发任何治理动作**。真正的瓶颈在于**各 Agent 底层原生会话（`thread_id`）会随着轮次不断累积 token**，且机械截取首尾摘录在几十轮后会丢失关键共识。

需要按“**先隔离 → 分级水位线压缩/轮转 → 防死循环与透明化 → 滚动检查点 → 消息级分叉**”五层来治理：

#### 4.1 子任务上下文隔离（治本）
- 阶段二的委派子任务始终跑在独立的 `runtime_conversation_id` 上，只携带主 Agent 提炼的精确指令、相关文件路径与必要工作区依据，**绝不继承主会话全量历史**；子任务完成后只将最终结论与工具摘要回传给主会话，从源头延缓主上下文膨胀。

#### 4.2 基于 `context_usage` 三级水位线的分层压缩与无缝轮转
复用 `src-tauri/src/agent_commands.rs` 中已有的 `conversation_context` 数据源和前端 `src/features/chats/ContextMeter.tsx`，在每轮真正发送给模型前检查目标 Agent 的上下文占用比例：
- **`< 70%`（正常区）**：正常运行，不做干预。
- **`70% – 80%`（预警区）**：`ContextMeter` 提示预警态，并在其旁提供**「整理上下文」**手动触发按钮，允许用户主动提前轻装上阵。
- **`≥ 80%`（自动治理线，受设置开关控制，默认开启）**：
  1. **支持原生压缩的运行时**（如支持 `/compact` 的 CLI 运行时）：先触发一次原生上下文压缩，记录压缩前后的 token 数（`pre_tokens → post_tokens`）。
  2. **不支持原生压缩的运行时（或原生压缩后仍 `≥ 75%`）**：自动执行**底层会话无缝轮转（Thread Rollover）**：
     - 后端基于“用户原始目标 + 阶段检查点摘要 + 最近 3–5 轮原文”组装一份交接背景；
     - 为该成员在对应的运行时会话表（`codex_sessions` / `gemini_sessions` / `claude_sessions` / `deepseek_sessions`）中切换到新的干净 `thread_id`；
     - 将交接背景作为新底层会话的首条上下文注入，无缝继续下一轮；
     - **前端聊天记录完全不断层**，用户看到的仍是连续的同一条对话。

#### 4.3 防死循环冷却机制与 UI 透明化
- **防“反复压缩死循环”冷却机制**：
  - 在会话状态中记录 `last_compacted_sequence`（或最近一次压缩轮次），**至少间隔 3 轮**才允许再次自动触发压缩/轮转；
  - 若刚完成一次压缩/轮转后，下一轮上下文占用仍直接超过 80%（例如单次工具输出过大），直接暂停自动协作并提示用户手动精简或分叉新会话，绝不陷入反复压缩死循环。
- **UI 过程完全透明**：
  - 压缩/轮转执行期间，状态栏单独显示明确状态（如 `正在整理上下文…`），不混入普通的“正在处理”转圈；
  - 完成后在聊天时间线插入一条轻量系统提示，明确展示变化结果（例如：`已整理上下文 · 182k → 34k tokens（历史记录已保留）`）；
  - 在设置中提供“接近上下文上限时自动整理”开关，支持用户关闭自动压缩、改为纯手动控制。

#### 4.4 升级群聊历史摘要：滚动检查点摘要
- 替换 `src-tauri/src/group_context.rs` 中仅截取“前 240 字 + 后 160 字”的机械摘录策略。
- 每经过固定轮数（如每 10 轮）或触发底层轮转时，生成一份结构化检查点（包含：**已达成共识、未解决分歧、已核验文件路径与关键结论、待办返工项**），持久化到摘要表；后续轮次只注入“最新检查点 + 最近几轮完整消息 + 按需检索片段”，确保聊到第 50~100 轮时依然不跑偏、不失忆。

#### 4.5 超长任务终极兜底：消息级「从这里分叉新会话（Fork）」
- 在 `src/features/chats/ChatStage.tsx` 每条助手消息的操作栏（现有“回复 / 沉淀到知识库 / 复制”）新增 **「从这里分叉」** 按钮：
  - 基于截至该条消息的结构化摘要 + 当前工作区路径与知识库绑定，一键创建一条干净的新会话继续推进；
  - 原超长会话完整保留或按需归档，为超长任务提供彻底的“换脑”出口。

#### 4.6 验收标准
- 上下文占用达到 70% 时前端展示预警与手动「整理上下文」按钮；达到 80%（开启自动整理时）能自动完成压缩或底层 `thread_id` 无缝轮转，聊天流不断层且时间线展示压缩前后 token 变化。
- 连续两轮触发高占用时受 3 轮冷却保护，不会陷入反复压缩死循环。
- 点击任意助手消息的「从这里分叉」可生成携带前置摘要的新会话，且原会话历史不受影响。

## 4. 实施优先级建议

1. **P0（立即实施）**：阶段一（群聊多轮自主讨论提示词优化 + 上限放宽至 100 轮）。改动集中在 3 个 Rust 文件，无迁移风险，可立刻改善群聊协作体验。
2. **P1（核心迭代）**：阶段二（单 Agent 会话按需委派 + 子任务卡片 UI）与阶段四（长轮次上下文压缩/轮转治理）。解决“单聊中途需要另一模型协助”以及“长轮次讨论爆上下文”两个核心痛点。
3. **P2（按需补充）**：阶段三（单聊一键派生群聊）。在阶段二落地后，视真实使用频次决定是否排期。
