# 群内成员并行执行

不写 @ 时，消息广播给群内全部成员，两家分别启动并自行协调分工。明确 @ 时，只发给被点名的成员；只点名一位时，后台阻止该轮回复自动唤醒另一位。同时在普通正文 @Codex 和 @DeepSeek 时，两家分别启动，不等待对方回复。同一成员一次只执行一轮，后续消息进入该成员队列。其他群和私聊保持原有执行准入限制。

```text
用户同时 @ 两位 ─┬─ Codex 执行 ──── 独立回复与归档
                └─ DeepSeek 执行 ─ 独立回复与归档
```

成员状态条分别显示启动、处理、等待批准、完成、错误及待处理数。一位完成或失败后，另一位继续执行。Codex 的审批不会因 DeepSeek 同时运行而消失。暂停只阻止后续轮次；停止取消两位成员及未执行队列。重启保留记录，不重发旧任务。

数据库升级至 schema 12。迁移前备份 schema 11 数据，新增按任务和成员区分的会话、轮次、投递来源和状态。轮次归档按任务与成员匹配，避免归档另一位尚未结束的回复。Agent 交接保留资料属性，不进入用户授权消息列表。

已验证：

- Rust 自动测试：两位同时活动、独立归档、成员队列互不阻塞、失败隔离、交接去重、暂停恢复、取消两位、取消失败仍尝试另一位、重启恢复及 schema 11 迁移备份。
- 真实 Codex 和 DeepSeek 各执行一轮：确认两家在同一时刻均处于活动状态，随后正常完成，结果独立归档。
- 前端状态组件测试和 TypeScript / Vite 构建。
- 浏览器挂载实际 ChatStage 组件，使用状态样本核对“两位处理”和“一位完成、另一位继续”。截图位于 `artifacts/parallel-members/`；浏览器状态样本不冒充真实执行。

限制：两位仍共享群工作目录，未创建独立 worktree。并行写同一文件存在冲突风险。提示要求先协调文件分工并在写入前重新读取；快照可能含双方及原有修改，不能用快照差异认定单个成员的文件归属。真实集成验证使用无工具文本任务，没有验证并行改写同一文件，也没有对真实双模型执行取消验证。

补充验证：前后端共用十组路由样例，覆盖默认广播、单独点名、正文中点名、多位点名、去重、引用、代码、邮箱和单成员群。调度回归验证广播启动两位、单独点名只启动一位，且该轮回复不能自动转交另一位。分工通过模型提示和群内交接完成，没有增加自动组长或文件锁。

## 工具开放与按任务分工更新

用户要求两家开放运行时实际支持的工具，不再固定 DeepSeek 负责文件、Codex 负责命令或浏览器。已移除 DeepSeek 启动补丁中的 `tool-pwsh` 和 `tool-plugin-manager` 禁用项，保留日志隐私、工作区权限与审批配置。浏览器等能力取决于各自运行时实际安装与提供的工具，没有新增浏览器驱动或伪造工具能力。

广播和群聊提示改为：普通问候、闲聊只简短回应，不调用工具、不分工、不总结历史项目；收到具体任务后再协商分工。明确要求以当前工具清单为准，不沿用历史中的禁用说明。界面已移除“文件任务专属”和“终端禁用”的旧说明。

真实 PowerShell 试验：模型调用了 `pwsh`，工具返回 `(no output) [exit code: 3221225794]`，即 `0xC0000142`。因此工具开放已确认，命令执行仍未通过；没有改成无沙箱执行，没有运行系统文件权限修复。该失败保留在显式忽略的真实集成测试 `installed_deepseek_enabled_powershell` 中，普通测试不调用真实模型。

真实群聊问候验证通过：只发送“你们好”，DeepSeek 回复“你好！我是 DeepSeek，很高兴见到你们。有什么需要帮忙的，随时告诉我。”未调用工具，未介绍固定分工或历史工作区。普通 Rust 测试 29 项、前端测试 14 项及前端生产构建通过；真实终端试验的失败单独记录，不计入通过结果。
